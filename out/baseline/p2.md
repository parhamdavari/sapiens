Short version: it's a timezone bug, but not quite the one the setup suggests — and the direction of the failure is worth a second look before you patch anything.

The key detail is that `DATE(created_at)` is evaluated by the database, not by Python. So the thing deciding which calendar day `2026-03-01T23:30:00Z` falls into is the **database session's** timezone, not the `TZ` of the process running pytest. Those are the same thing when you run the DB locally alongside the tests, and they very often differ in CI, where the database is a separate service with its own environment.

Walking the seed data through both cases:

- `2026-03-01T23:30:00Z`
- `2026-03-02T00:15:00Z`
- `2026-03-02T04:00:00Z`

In UTC you get two groups — `2026-03-01` (one order) and `2026-03-02` (two) — so `result[0]["day"] == "2026-03-01"` passes. At UTC+1 the first row slides to 00:30 on the 2nd, all three collapse into a single `2026-03-02` group, and `result[0]` becomes `2026-03-02`.

Which is why the numbers point the wrong way: the failure you're getting (`'2026-03-02' == '2026-03-01'`) is the UTC+1 result, but UTC+1 is your laptop's offset, and CI is the side that's failing. So either CI's database isn't actually running in UTC — an unset `TZ` in the app container says nothing about the DB service — or the local run isn't exercising the same path.

Two quick things to confirm that:

1. On CI, run `SELECT current_setting('TIMEZONE')` (or `SELECT @@session.time_zone` on MySQL) on the same connection the test uses. I'd expect it not to be UTC.
2. Print the whole `result`, not just `result[0]`. One row versus two tells you immediately whether this is a grouping-boundary problem or an ordering problem.

The fix is the same either way: make the query timezone-explicit instead of inheriting whatever the server has.

```sql
SELECT DATE(created_at AT TIME ZONE 'UTC') AS day, SUM(total) AS total
FROM orders GROUP BY day ORDER BY day
```

That's worth doing regardless of the test — daily totals grouped by "whatever timezone the server happens to be in" is a production bug too. If those totals are meant to be reported in a business timezone rather than UTC, name it explicitly (`'Europe/Amsterdam'`) and use the same string everywhere.

Then, on the test side, either pin the DB session timezone in a fixture or move the seed timestamps away from midnight. Right now they sit 30 minutes either side of a date boundary, so the test is checking your timezone configuration as much as it's checking the grouping logic.
